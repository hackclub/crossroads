# How the backend works

A tour of `backend/` for whoever changes it next, human or Claude. Read this before editing. [DEVELOPMENT.md](DEVELOPMENT.md) covers running and testing it, [ROUTES.md](ROUTES.md) its routes, and [INTEGRATING.md](INTEGRATING.md) building a frontend on it.

## What it is

Crossroads is a Hack Club YSWS ("You Ship, We Ship") for an in-person event. Teenagers build projects, tracking their time with Hackatime. Reviewers approve the time. Approved hours earn **stamps**, the currency. 60 approved hours earns enough stamps to buy a **ticket** to the event in the **shop**, which also sells physical items and travel stipends. Milestones of approved hours give **boxes** (like loot boxes) that drop collectible **special stamps**, some of which can be used on a submission (today, only for priority review).

The backend is a Go server (chi router) on Postgres. Postgres is the source of truth, and a background job copies approved submissions and shop orders into the "YSWS - Crossroads" Airtable base for the Hack Club team.

## A request's path

1. chi's `Logger` and `Recoverer` middleware, then `auth.LoadSession`. It hashes the `crossroads_session` cookie, looks up the session and its user, and puts a `*db.User` in the request context. The user is read fresh on every request, so role changes and new balances apply immediately.
2. `/auth/*` goes to `auth.Auth.Routes()`. `/api/*` goes to `api.API.Routes()`, which requires a user for everything, plus `RequireRole(reviewer, admin)` on `/api/review` and `RequireRole(admin)` on `/api/admin`.
3. A handler usually:
   - gets the user with `auth.User(ctx)`
   - reads path IDs with `idParam` and the body with `decode`; both respond themselves and return false on failure
   - validates, often with an `apply` method that copies fields onto a row and returns a problem to show the person
   - opens a transaction (`a.Pool.Begin`, `a.Queries.WithTx(tx)`) and takes row locks in the order described under "Locking"
   - runs sqlc queries
   - finishes with `respond.JSON`, `respond.Error` (a message for the person) or `respond.ServerError` (which logs the details and hides them)

Responses always use explicit JSON structs with `snake_case` tags. Never return sqlc models directly: they have no JSON tags and contain things participants mustn't see, like `hca_id` and reviewers' internal notes.

### Where each rule is enforced

Rules live in the database wherever possible, so a bug in Go can't break them. Several have tests that fail if the protection is removed.

| Rule | Enforced by |
|---|---|
| One ship in review per project, at any stage | unique partial index `submissions_one_open_per_project` |
| A ship's hours are set exactly when it's past the first stage and not rejected | check `submissions_approved_seconds_set` |
| Each stage's reviewer and time are set together | checks `submissions_reviewer_set`, `submissions_reviewed_at_set`, `submissions_fraud_review_complete`, `submissions_hq_review_complete`, `submissions_claim_complete` |
| Nothing pays before HQ signs off | Go: `decide` only calls `payOut` when the ship becomes `approved` |
| The fraud check only cuts hours | Go: `decide` |
| A decision applies to the stage the reviewer saw | Go: `decide` checks `stage` against the locked row |
| Nobody decides a ship someone else holds | Go: `checkClaim`, under the submission's row lock |
| Two Nexts never claim the same ship | `FOR UPDATE SKIP LOCKED` in `ClaimNextSubmission` |
| A reviewer can't approve more than the submission claimed | check `submissions_approved_within_new` |
| A Hackatime project counts toward one project, and only one of its owner's | primary key on `project_hackatime_projects`, plus a composite foreign key to `projects (id, user_id)` |
| A submission pays out once | unique index `stamp_ledger_one_payout_per_submission` |
| An order is charged once and refunded at most once | unique index `stamp_ledger_one_entry_per_order_kind` |
| The ledger is never edited | trigger `stamp_ledger_append_only` |
| `users.stamps` always equals the ledger's sum | trigger `stamp_ledger_apply` (function `apply_stamp_entry`) |
| A purchase can't take a balance below zero | the same trigger raises `stamps_not_negative`; Go checks with `db.IsNotEnoughStamps` |
| One box per milestone per person | unique `(user_id, milestone_id)` on `boxes` |
| No stacking: at most one special stamp per submission | unique `special_stamps.submission_id` |
| A box drops exactly one stamp | unique `special_stamps.box_id`, and the box row is locked while opening |
| Supply caps hold | the conditional update in `ClaimSpecialStampSupply` |
| Tickets are one per person; stipends have an amount; stock never goes negative | checks on `shop_items`, plus the locked item row when buying |
| Every box type keeps an unlimited stamp type | Go: `adminSetBoxDrops` and `adminUpdateSpecialStampType` (`BoxTypesOnlyUncappedBy`) |
| Paid-out Hackatime projects can't be unlinked | Go: `setHackatimeLinks`, using the paid set from `accountedFor` |
| Projects can't change while waiting for review; submitted ones can't be deleted | Go: `updateProject`, `deleteProject` |
| Nobody reviews their own project | Go: `decide`, `addComment`, `claimSubmission`, and Next's query |

## Hours accounting

This is the subtlest part, and it exists to stop the same time being paid twice ("prevent duping wherever possible" was the brief).

Time comes from Hackatime's `GET /api/v1/users/{slack_id}/stats?features=projects&start_date=…&filter_by_project=a,b`, counting from `hoursStart` (midnight UTC, Oct 30 2026). Hackatime itself counts overlapping time once within a filtered total, but separate calls for separate projects each count it in full.

A submission's `new_seconds` is `hackatimeTotals.unclaimed`, the smaller of two limits, and never below zero:

1. **The project's limit:** its Hackatime total minus what its approved submissions have already covered (`accountedFor`: the sum of their `new_seconds`). That sum deliberately uses `new_seconds`, not `approved_seconds`, so time a reviewer cut can't be claimed again.
2. **The person's limit:** their Hackatime total across **every** Hackatime project they've linked to any project (overlaps counted once) minus everything their pending and approved submissions have claimed (`ClaimedSecondsForUser`).

The second limit catches:
- the same hours counting toward two projects at once, like client and server worked on side by side
- renaming a Hackatime project, which moves its time under a new name
- linking the same time somewhere else after it's paid

Rejected submissions aren't counted as claimed, so their time goes back into the pool.

To keep this airtight under concurrency, `submit` asks Hackatime first (it's slow), then locks the person's `users` row, re-reads all their links, and gives up with `409` if they changed in the meantime. Creating, editing and deleting projects also lock the `users` row, so links and submissions for one person change one at a time. `api/dupes_test.go` holds two submissions at a barrier to prove the lock matters.

Other protections:
- Each submission records the Hackatime projects it counted. Once one is approved, those links are fixed to that project.
- Hackatime's trust level `red` (caught cheating) blocks submitting.
- Reviewers see Hackatime's current numbers, whether the account is flagged, and any other projects sharing the repo or demo link.

`GET /api/projects/{id}` shows `unsubmitted_seconds` using the same function, so the number shown is exactly what a submission would claim.

## Stamps

- Every change goes through `stamp_ledger`. Its trigger adds the amount to `users.stamps` and refuses a purchase that would go below zero. **Never update `users.stamps` directly, and never edit ledger rows**; add an adjustment instead.
- Only purchases are blocked from going negative. Adjustments can take someone below zero, which is how stamps from a fraudulent project are clawed back after they've been spent.
- **Payouts** happen when a submission is approved. `stampsFor(s) = s × STAMPS_PER_HOUR / 3600`, rounded down, and each approval pays `stampsFor(total after) − stampsFor(total before)` over the person's approved seconds. Working from the running total means rounding never costs anyone a stamp: 60 approved hours is always exactly 60 hours' worth, however it was split. If the rate changes, only new hours use the new rate.

## Reviewing

The stages, the checks and Sidekick are explained in [REVIEW_FLOW.md](REVIEW_FLOW.md). The code:

`decide` (`stages.go`) applies every decision, from the review pages and from Sidekick alike:
1. Validate the decision. For a first-stage approval, run the automatic checks (`runChecks`, which asks Hackatime) **before** taking any locks, because Hackatime is slow.
2. Lock the owner's `users` row, then the submission. Decisions for one person go one at a time, so running totals are right.
3. Refuse it if the ship isn't in review, has moved on from the `stage` the reviewer saw, is a stage they can't decide (`permissions`), or someone else holds it (`checkClaim`).
4. Work out the ship's new state in Go, then write it all with `SaveSubmissionReview`, which also drops the claim. Add the `ship_events` row for the decision (and a `flagged` one if the checks sent it to the fraud check).
5. If it's now `approved`, `payOut`: read the new running total, pay the difference in stamps plus any Golden Spike bonus, and grant a box for every milestone at or below the new total.

Sidekick passes its own `permissions`: it vouches for its reviewers, so `isHq` decides whether an approval signs off. Everything else is the same code.

`runChecks` is also what the review page and Sidekick's project detail show, run fresh on each load. What it said at the moment of approval is saved on the submission (`checks`).

The queues put submissions with a priority-review special stamp first, then oldest first. `ClaimNextSubmission` uses the same order, after the reviewer's own live claim.

## Boxes and special stamps

- **Opening** (`openBox`): lock the box, load its drops whose stamp types still have supply, and pick one at random weighted by `weight`, using `crypto/rand`. Then claim one from that type's supply with a conditional update. If that finds nothing, someone else just took the last one, so drop it from the list and roll again. Then create the special stamp and mark the box opened.
- **Odds** (`GET /api/box-types`) use the same availability rule, so what's shown is what happens.
- **Supply caps** count issued stamps, not used ones, so a stamp someone holds always works. Admin grants come out of supply too. Lowering a cap below what's issued just stops new drops.
- **Every box type must keep at least one unlimited stamp type**, so a box can never come up empty. This is enforced when setting drops and when capping a type.
- **New milestones** are granted straight away to everyone already past them (`GrantMilestoneToQualifiedUsers`).
- **Claim links**: a stamp type with a `claim_code` can be claimed at `/claim/{code}` on the platform, for handing out a stamp with an announcement. Claims come out of supply like everything else. A claimed stamp has `claimed` set instead of a `box_id` or `granted_by` (the `special_stamps_source` check), and the partial unique index `special_stamps_one_claim_per_type` keeps it to one per person per type, even with simultaneous requests.
- **Using a stamp** happens when submitting. It has to be theirs, unused, and have an effect. It's used up whatever the outcome.
- **Adding an effect** (say, the stamp multiplier, deferred for budget reasons):
  - add the enum value in a new migration (`alter type special_stamp_effect add value '…'`)
  - apply it where it matters; a multiplier would go in `reviewSubmission`'s payout
  - give it a cap like a `max_bonus`, so worst-case spend is `supply_cap × max_bonus`

## Shop

`buy`:
1. Check verification. This happens before the transaction because it may call Hack Club Auth: if the saved status isn't verified and eligible, ask the public check endpoint and save what it says.
2. Lock the buyer's `users` row, then the item.
3. Fill in the shipping address from `users.address` if none was sent.
4. Check `max_per_user`, stock, and the balance (only for a friendlier message).
5. Work out the price: the launch sale (`api/sale.go`: 10% off everything but tickets and price locks until `API.SaleEnd`), then tickets and price locks, below.
6. Create the order, then the purchase ledger entry. The ledger trigger is the real guard against overspending.
7. Take one from stock.

Orders keep the price paid. Admins can move a pending order to `fulfilled`, or to `cancelled`, which refunds the stamps and restocks the item.

**Ticket batches and price locks** (`api/tickets.go`). A ticket with `batch_size` and `batch_step` costs `price + batch_step × floor(sold / batch_size)`, where `sold` counts its orders that weren't cancelled. That's counted under the ticket's row lock, so buyers at the same moment each get the right batch. A cancelled ticket goes back on sale, so it can bring the price back down a batch.

A price lock is its own shop item. Buying one locks the ticket's row too (after the lock item's) to read the batch on sale, and saves that price as `orders.locked_price`. A lock order starts `fulfilled`, since there's nothing to send, so it never sits in the fulfilment queue. Buying the ticket then costs the lower of the batch on sale and their lock. Locks are refused once someone has a ticket, once the tickets are sold out, and on the last batch, where the price can't go up.

A lock doesn't hold a ticket. When the tickets sell out, `RefundPriceLocks` cancels and refunds every lock whose holder has no ticket, each in its own transaction that locks the holder first. It runs right after the last ticket is bought, and every 10 minutes from `main.go`, which also catches an admin setting the stock to 0. Price lock orders aren't copied to Airtable.

## Signing in

- Standard OAuth code flow against Hack Club Auth, using `golang.org/x/oauth2`, with a random `state` in a 10-minute cookie scoped to `/auth/`.
- The callback swaps the code for a token, calls `GET /api/v1/me` and upserts the user by `hca_id`. **The access token isn't kept**; everything is refreshed at the next sign-in.
- Scopes are `email name slack_id verification_status basic_info address`. The last two need the app's `hq_official` trust level.
- The session token comes from `crypto/rand`. The cookie holds the token and the database holds only its SHA-256, so a database leak can't be used to sign in. Sessions last 30 days, and a person's expired sessions are cleaned up when they sign in.
- `next` redirects only go to paths on this site (`safeNext`).

## Airtable sync

`airtablesync.Syncer` runs every 30 seconds inside the server when `AIRTABLE_TOKEN` is set. Each pass:

1. **Submissions:** approved ones without an `airtable_record_id` become rows in **YSWS Project Submission**, then get the record ID saved so they're never copied again. The field mapping is in `submissionFields`:
   - approved hours go in "Optional - Override Hours Spent", with a justification
   - Hackatime project names, the date range and the Slack ID go in the justification fields
   - address and birthday come from Hack Club Auth
   - updates to an already-approved project get "Optional - Override Duplicate Justification"

   It **never** touches the Automation fields, "Grant fulfilled", "Under inspection" or the survey fields. In particular, a person ticks "Automation - Submit to Unified YSWS" after checking the row.
2. **Fulfilled orders:** Shop Orders rows with **Fulfilled** ticked and Status `pending` mark the matching order fulfilled.
3. **Orders:** new ones (no record ID) are created, and changed ones (`updated_at > airtable_synced_at`) are updated. `airtable_synced_at` is set to the `updated_at` that was copied, so a change made during the copy goes next time. Migration 7 narrows the orders `updated_at` trigger to real order columns; otherwise recording a sync would itself count as a change, and orders would be copied forever. The sync never writes **Fulfilled** or **Fulfillment Notes**, which belong to whoever ships things.

Details:
- Fields are addressed by name, so renaming a column in Airtable breaks the sync. It logs the error and retries every pass.
- Requests go in batches of 10, at most 4 a second (Airtable allows 5), with `typecast` on.
- If Airtable accepts a new row but saving its record ID fails, the next pass adds it again. This is rare, and the cost is a duplicate row.
- Only one server instance should run the sync.

## Activity

`activity.Poller` runs every 30 minutes inside the server and records how much time each project got on each UTC day, for `GET /api/admin/activity`. Each pass:

1. Takes a Postgres advisory lock, so only one server instance polls; the others skip the pass.
2. Lists projects with linked Hackatime projects whose owner has a Slack ID.
3. Asks Hackatime for each one's heartbeat spans (`/users/{slack_id}/heartbeats/spans`, filtered to the linked projects), splits them at UTC midnight and adds them up per day. Spans add up to the same total as the stats call.
4. In one transaction per project, deletes its rows for the days covered and writes the new ones, so time that moves between projects (relinking) or disappears ends up right.

The first pass each UTC day covers everything since Hackatime time starts counting (Oct 30), which picks up relinked projects and late heartbeats. The rest cover yesterday and today. Private or missing Hackatime accounts are skipped; other errors are logged and retried next pass.

`activity.Visits` is middleware, right after `auth.LoadSession`, that records platform use. A signed-in person's first request each UTC day adds a `platform_activity` row; the server then remembers that day in memory, so their later requests don't touch the database. Several instances each remember on their own, which only costs an insert that does nothing. A failed insert is logged and retried on the person's next request. Migration 10 filled in earlier days from existing sessions' sign-in times. Sign-ups per day come from `users.created_at`.

## Locking

Anything that changes a person's stamps, links or submissions locks their `users` row first. The orders, so no two transactions can deadlock:

- projects: user → project → special stamp
- reviewing: user → submission (the ledger trigger updates the same user row)
- buying: user → shop item (a price lock: user → price lock item → ticket)
- refunding a price lock: user → order
- cancelling an order: order → user (through the ledger) → shop item
- opening a box: box → special stamp type

Keep new code to these orders.

## Conventions

- **Comments** explain why, not what. Match the existing density.
- **Error messages** are for participants: plain, specific, and telling them what to do next. The frontend shows them as is.
- **Units:** seconds for time, whole stamps, cents for money.
- **PATCH bodies** use pointer fields for "left out = unchanged", and `optional[T]` (in `admin.go`) where `null` has to mean "clear it".
- **Tests:** one test per behavior, against a real Postgres. Fakes for outside services live in the test files. Concurrency tests hold requests at a barrier. When you add a protection, check that its test fails without it.
- **Commits:** short, lowercase subject lines. Don't add AI co-author trailers.

### Recipe: adding an endpoint

Say, letting participants see milestones (`GET /api/milestones`):

1. **Query:** `ListMilestones` already exists in `db/queries/boxes.sql`. For a new one, add it there and run `go generate ./db`.
2. **Handler** in the right `api/*.go` file: get the user, read input, check it, open a transaction if writing (lock the user first), query, and respond with an explicit JSON struct.
3. **Route** in `api/api.go`, in the right group (participant, `/review` or `/admin`).
4. **Test** in the matching `api/*_test.go`, using `newEnv`, `newUser`, `newReviewer`, `newAdmin` and `mustCall`.
5. **Document** it in `planning/ROUTES.md`.

## Decisions, and why

Settled with the organizer while building this (Nov 3 and 4, 2026):

- **Postgres as the source of truth, synced one way to Airtable.** The shop needs transactions so nobody can spend the same stamps twice, and Airtable has none (and a limit of 5 requests a second).
- **Rates and qualifying:** 30 stamps per approved hour. The ticket costs 60 hours' worth (1,800) in its first batch, then 5 hours more for each batch of 6 after that, up to 80 hours for the last of the 30. A price lock costs 5 hours' worth and is on top of the ticket, so it pays off only if the price would have gone up two batches or more (decided 2026-11-06). Qualifying means buying the ticket, so spending stamps on other things delays it.
- **Launch sale:** for the shop's first week, until midnight UTC on Nov 13 2026, everything is 10% off except the ticket and price locks, so qualifying still takes 60 hours (decided 2026-11-06).
- **Hours count from midnight UTC on Oct 30 2026 (the day the RSVP page first went up; moved from Nov 3 on Nov 6), and only approved hours count,** totaled across all of a person's projects.
- **Verification:** submitting doesn't need Hack Club Auth verification. Buying needs a verified identity that HCA says is YSWS-eligible.
- **Milestones count approved hours, not raw Hackatime hours,** so they can't be farmed. The catch is that the first box only arrives after the first approval.
- **Special stamps:**
  - Multiplier stamps are deferred until there's budget.
  - Supply caps exist so the budget for special stamps can be controlled.
  - Pools are first come, first served, with no release schedule.
  - No stacking: one special stamp per submission.
- **Boxes are only ever earned, never sold, and their odds are shown,** because participants are minors.
- **Resubmitting is allowed and only pays for unclaimed time.** Reviewers can approve part of the time; time they cut is gone for good, while rejected time can be submitted again.
- **Admin adjustments can go negative,** for clawbacks.
- **Airtable:**
  - approved submissions go to the existing YSWS Project Submission table, and a person ticks the Unified YSWS box
  - orders go to a new Shop Orders table
  - ticking Fulfilled there flows back to the backend
- **The HCA app is `hq_official`,** so sign-in collects the address and birthday the Unified YSWS DB needs.

## Known gaps and ideas

- **Frontend-facing:**
  - participants can't list milestones
  - `/api/me` doesn't include the address on file
  - there are no live updates and no pagination
- **Cross-site deployment** would need CORS with credentials, `SameSite=None` cookies and CSRF tokens. Today it relies on being same-origin, plus `SameSite=Lax` and JSON bodies.
- **No rate limiting.** Submitting calls Hackatime twice per request.
- **No graceful shutdown,** and no Dockerfile or deployment config.
- **Admin editing is incomplete:** milestones can't be edited or deleted, and stamp types and box types can't be deleted. A review can't be undone; fix mistakes with stamp adjustments. Fulfilled orders can't be cancelled.
- **Airtable leftovers:**
  - submission rows aren't updated after they're added
  - a stipend's dollar amount is read from the item at sync time rather than saved on the order
- **Event-day features** (check-in, waivers, travel logistics) aren't built.
- **Hackatime requires public stats.** Hackatime's OAuth could replace that.
- **Sign-in hasn't been tried with a real account yet.** The tests use a fake Hack Club Auth built from its docs. The first real sign-in should confirm that it works, and that the `basic_info` and `address` scopes fill in the birthday and address.
